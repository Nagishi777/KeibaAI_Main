## 3. 設計

### 3.1 実行方法

```bash
# レース当日: 1m時点オッズを取得して予測・ベット推奨を出す
python -m src.simulator.predict_today --fetch

# 取得済みCSVから予測だけ行う（再実行・検証用）
python -m src.simulator.predict_today --date 2026-07-18

# レース後: 確定着順を加えてモデルを更新する
python -m src.simulator.retrain --start-period 202401 --end-period 202507
```

処理の流れは仕様書 §1 のブロック図をそのまま写している。

```
[1] 5m時点と1m時点のオッズ・総票数を取得   ← realtime_odds（--fetch）
      ↓
[2] 馬番別の投票額を逆算                  ← features.build_features
      ↓
[3] 特徴量2列: odds_1m / inc_share_5m_1m   ← features.attach_features
      ↓
[4] LightGBMで各馬の勝率を予測             ← predict_today.predict_proba
      ↓
[5] pool_1m < しきい値 のレースは丸ごと見送り ← predict_today.select_bets
      ↓
[6] EV = 予測確率 × 1mオッズ >= 1.10 を買う   ← 同上
      ↓
[7] 賭け金は fractional Kelly / 1レース3点  ← 同上（既存の評価器を呼ぶ）
```

### 3.2 学習と当日でロジックがずれない構造

本実装で最も重視したのはこの点である。バックテストで検証した戦略と、
当日実際に動く戦略が別物になっては意味がない。

**特徴量の定義を1箇所に閉じ込めた。** 学習側（`retrain`）は月別CSV
（`data/processed/odds_series`）を読み、当日側（`predict_today`）は時点別CSV
（`data/processed/realtime_odds`）を読む。**入力ファイルの形式は違う**が、
どちらも `features.attach_features()` という同じ関数を通す。整形の差は
`realtime_loader` が吸収し、特徴量の計算式は共有される。

この同値性はテストで固定している（`test_realtime_and_training_paths_agree`）。
当日形式と学習形式に同じ内容を与え、出てくる特徴量が一致することを検証する。

**賭け金の計算も既存の評価器をそのまま呼ぶ。** Kelly計算を書き直さず、
バックテストが使う `ModelEvaluator._kelly_criterion_vec` を呼ぶ。
1レース最大点数の選抜基準（EV順ではなく**予測確率順**）も
`src/backtest/stats.py` の `extract_bet_rows` と同一である。

**列順も固定した。** `features.feature_frame()` を経由させ、学習時と推論時で
LightGBM への列順が食い違わないようにしている。列順がずれると予測が
黙って壊れるため。

### 3.3 未来を見ない担保

| 担保 | 実装 |
|---|---|
| しきい値 | 学習期間の分布から決め、`_simulator.json` に固定値として保存。予測側は読むだけで、当日のレース群から取り直さない |
| early stopping / 校正 | 学習期間末尾6ヶ月の holdout でのみ行い、fit期間には触れさせない |
| 特徴量 | 5m / 1m の締切前スナップショットのみ。確定オッズ・確定票数・払戻は参照しない |
| 賭け判断オッズ | 1m時点（特徴量と同じ時点。仕様書 §6「時点のズレを消した本番相当の設定」） |

しきい値を保存する理由を補足する。仕様書 §5.2 は「学習期間の分布から75%分位点を取り、
その**固定値**を検証期間に適用する」と定めている。もし予測時に当日のレース群から
分位点を取り直すと、「その日たまたま厚かったレース」を基準にすることになり、
未来を見ない前提が崩れる。よって学習時に確定させ、モデルと対で持ち回る設計にした。

### 3.4 欠損を補完せず停止する方針

CLAUDE.md の「想定外の状況では値を補完せず処理を止める」に従い、以下は停止・除外する。

| 状況 | 扱い |
|---|---|
| 1m のオッズが取れていない馬 | **除外**（5mで代用しない） |
| 着順が結合できない行がある | **停止**（ValueError） |
| `_simulator.json` が無い | **停止**（しきい値不明で全レースを賭けてしまうため） |
| キャリブレータが無い | **停止**（校正前の確率でEV・Kellyが静かに壊れるため） |
| 特徴量が算出できる行が0件 | **停止** |

1m を 5m で代用しない点は特に重要である。代用すると増分が0になり
`inc_share_5m_1m` が「直前1分に資金が動かなかった」と**誤って断定**することになる。
これはモデルが最も重視する特徴量（importance 96%）なので、偽の0を入れてはならない。

## 5. 実装上の判断

### 5.1 `pool_1m` を特徴量にしなかった

仕様書 §5.4 は、`pool_1m` をモデルの特徴量に加えると回収率が **-22〜-31ポイント
悪化**したと記している。レース内の全馬に同じ値が入るため馬の序列化に寄与せず、
木が無駄な分割を消費して確率の校正が壊れるためである。

そこで `FEATURE_COLS`（モデル入力）と `POOL_COL`（フィルタ用）を別の定数として
定義し、`pool_1m` が誤って特徴量に混ざらないようにした。テストでも固定している。

### 5.2 EV しきい値を config から切り離した

`config/config.yaml` の `min_ev_win` は **1.05** だが、仕様書の条件は **1.10** である。
config の値は本体パイプライン向けに調整された別物なので、これを継承すると
仕様書と違う条件で動いてしまう。

初回実装では config を参照しており、実際に EV 1.05 で動作した。これを
`retrain.DEFAULT_MIN_EV = 1.10` として本条件固有の既定値を持つよう修正した。

### 5.3 ハイパーパラメータを spec の値で上書きした

`config/config.yaml` の既定は `num_leaves: 113` / `min_data_in_leaf: 100` である。
仕様書 §4 はこの設定について、2列に対して木が大きすぎ「1本目でholdout AUCが
飽和して early stopping が即発動し `num_trees=1` になる（片方の特徴量の
importance が 0 になる）」と明記している。

よって `SPEC_LGBM_PARAMS`（`num_leaves: 15` / `max_depth: 4` /
`min_data_in_leaf: 200` 等）で上書きする実装にした。config を使いたい場合は
`--no-spec-params` で切り替えられる。木が1本しか育たなかった場合は警告を出す。

### 5.4 既存ファイルへの変更（1箇所）

`src/simulator/scraping/realtime_odds.py` が `src.scraping._jvlink_o1` /
`src.scraping._jra_today_schedule` を import していたが、これらのファイルは
`src/simulator/scraping/` に移動済みで `src/scraping/` には存在せず、
**モジュールとして import できない状態**だった。

```
ModuleNotFoundError: No module named 'src.scraping._jvlink_o1'
```

当日予測から呼ぶ必要があるため、import 先を `src.simulator.scraping.*` に修正した。
これが既存ファイルへの唯一の変更である（当該ファイルは未コミット状態だった）。

> **追記:** その後 `src/simulator/scraping/` は `src/scraping/` と重複していたため削除し、
> 当日オッズ取得は `src/scraping/realtime_odds.py`（`python -m src.scraping.realtime_odds`）に一本化した。

## 6. 限界と未確認事項

### 6.1 木の本数が仕様書と違う（60本 vs 4本）

仕様書 §4 は「実際に育った木の本数: **4本**（early stopping）」と記しているが、
本実装では **60本** 育った。config の `early_stopping_rounds: 50` が効いた結果、
100本目まで学習してから60本目に戻る挙動になっている。

影響は次のとおり。予測確率がわずかに変わるため、EV が閾値近傍にある馬の
採否が入れ替わる。§4.3 のレースでは、EV 1.10 の条件下で6番（EV 1.083）と
8番（EV 1.073）が閾値を下回り、代わりに3番（138.3倍 / EV 2.185）が入った。
3番は仕様書が「EV は高いが**1レース3点上限**で次点に漏れた」と記した馬である。

importance比（96.4:3.6 対 99.4:0.6）とAUC水準は一致しているため、モデルの
性格自体は再現できている。仕様書の4本に厳密に揃える必要があれば、
`SPEC_LGBM_PARAMS` に `early_stopping_rounds` を追加すれば対応できる。

### 6.2 `--fetch` 経路が未実行

`--fetch`（JV-Link から当日オッズを取得する経路）は**実行検証できていない**。
JV-Link の実行環境と当日開催が必要なためである。

確認できたのは以下にとどまる。

- `realtime_odds.py` が import 可能になったこと（§5.3 の修正後）
- `get_today_schedule` / `run_scheduler` の呼び出しシグネチャが一致すること
- `--realtime-dir` が取得先と読込先の両方に渡ること

検証は、実データ（`data/processed/odds_series/202607`）を当日スクレイパの
出力形式に変換して行った。したがって「CSVができた後」は検証済みだが、
「CSVができるまで」は未検証である。**初回は開催日に `--fetch` を試し、
`data/processed/realtime_odds/` にファイルが生成されることを確認してほしい。**

### 6.3 戦略そのものの限界（仕様書 §8 の再掲）

本実装は仕様書の条件を忠実に再現したが、条件そのものが持つ限界は
実装では解消されない。

1. **多重比較のバイアス**: 108条件を試した中の上位条件であり、161.43% という
   回収率は上方バイアスを持つ
2. **単一分割**: 検証は12ヶ月・758レースのみ。過去の類例では単一分割107%が
   walk-forward 12フォールドで100.3%まで落ちている
3. **的中率3.85%の高分散戦略**: 58点の的中が全利益を生む構造
4. **1m時点で発注できる前提**: 実際の投票締切は発走の約1〜2分前であり、
   1mオッズを見て発注する時間的余裕があるかは運用側の検証が必要

また `market_feature_backtest_report.md` §5.1 は「市場特徴量のみのモデルは
実運用に値しない」「市場情報だけでは原理的に控除率を超えられない」と結論している。
本実装のモデルも市場特徴量2列のみである。

### 6.4 型チェックが未実行

CLAUDE.md は `mypy src/` を開発コマンドに挙げているが、本環境に mypy が
インストールされておらず**実行できなかった**。型ヒントは全関数に付けてあるが、
strict モードでの検証は未実施である。

### 6.5 フォーマッタを適用していない

`ruff format --check` は本実装のファイルを「要整形」と判定するが、
リポジトリ全体でも122ファイル中115ファイルが同様の判定になる。
リポジトリが `ruff format` で整形されていないため、周囲のコードスタイルに
合わせ、あえて適用していない。`ruff check`（リント）は通している。
