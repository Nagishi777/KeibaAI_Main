## 0. 結論

| 問い | 答え |
|---|---|
| 1日の後半のレースほど総投票数が増えるか？ | **本当。** 同じ日・同じ競馬場の中で Spearman +0.773、**1,031件中99.9%が正の相関**、負の相関は0件（§2） |
| どのくらい増えるか？ | 日内中央値比で **R1が0.79倍 → R12が1.88倍**。R1→R12 で約2.4倍（§1） |

## 2. 「後半ほど厚い」は統計的に確かか

同じ日・同じ競馬場ごとに「レース番号 vs 総投票額」の Spearman 相関を計算した
（1開催8レース以上を対象、R11は除外してメイン効果を排除）。

| 指標 | 値 |
|---|---|
| 対象（開催日 × 競馬場） | 1,031件 |
| 相関の中央値 | **+0.773** |
| 相関の平均 | +0.740 |
| **正の相関（後半ほど厚い）** | **99.9%** |
| 強い正の相関（≥ +0.5） | 91.0% |

## 3. R11の突出は「時間帯」ではなく「メインレース」

R11が跳ねるのは、遅い時間だからか、重賞だからか。
**同じ発走時刻帯の中で** R11と他レースを比べた。

| 発走時刻 | R11の中央値 | R11以外の中央値 | 倍率 |
|---|---|---|---|
| 15時台 | 15.58億円（n=998） | 8.06億円（n=613） | **1.93** |
| 17時台 | 7.72億円（n=21） | 7.78億円（n=28） | 0.99 |

**同じ15時台でもR11は他レースの1.93倍である。** 時間帯では説明できない。
一方、R11が無い17時台（最終レースなど）では差が消える。

よってR11の厚さは**番組の格（メインレース=重賞に資金が集まる）**によるもので、
「1日の後半だから」という時間効果とは別の要因である。

参考に発走時刻別の総投票額を挙げる（時間帯自体にも効果はある）:

| 発走時刻 | 中央値 |
|---|---|

| 11時台 | 4.93億円 |
| 12時台 | 4.99億円 |
| 13時台 | 5.10億円 |
| 14時台 | 6.08億円 |
| 15時台 | 10.69億円 |
| 16時台 | 9.92億円 |

## 5. フィルタ設計: 総投票額とレース番号のどちらを使うべきか

### 5.1 どちらも単体では効いて見える

採用条件（EV≥1.05 / 10〜150倍 / ドリフト≤-0.05 / 1レース1点）を
2026-02〜2026-07（1,617レース）に適用し、総投票額フィルタを外した751点を分類した。

**総投票額で絞った場合**（95%CIはレース単位ブートストラップ4,000回）:

| しきい値 | 点数 | 的中率 | 回収率(近似) | 95%CI |
|---|---|---|---|---|
| フィルタ無し | 751 | 6.13% | 140.6% | [95.6, 193.3] |
| ≥4億円 | 679 | 6.48% | 150.9% | [100.7, 209.5] |
| ≥5億円 | 543 | 6.81% | 156.2% | [99.2, 225.0] |
| ≥6億円 | 408 | 8.09% | 180.9% | [110.5, 268.3] |
| **≥7億円** | 307 | 8.47% | **200.7%** | [113.7, 309.9] |
| ≥8億円 | 230 | 8.70% | 222.2% | [111.5, 366.2] |
| ≥10億円 | 156 | 10.26% | 282.8% | [129.4, 484.6] |

**レース番号で絞った場合**:

| 条件 | 点数 | 的中率 | 回収率(近似) | 95%CI |
|---|---|---|---|---|
| 全レース | 751 | 6.13% | 140.6% | [94.0, 191.7] |
| R5以降 | 548 | 7.48% | 175.8% | [116.9, 246.0] |
| R7以降 | 437 | 7.09% | 174.3% | [105.4, 253.4] |
| R9以降 | 332 | 7.23% | 178.1% | [95.8, 278.7] |
| R10以降 | 273 | 6.59% | 176.6% | [84.3, 295.6] |

### 5.2 しかし両者は強く相関している（Spearman +0.765）

採用点の中でも総投票額とレース番号は +0.765 で相関する。
**片方の効果が他方に見えている可能性があるため、互いを固定して切り分けた。**

**レース番号を固定して総投票額の効果を見る**（各帯の中央値で2分割）:

| レース番号帯 | 薄い側 | 厚い側 |
|---|---|---|
| R1-6（前半） | 157点 **57.9%** | 157点 **129.7%** |
| R7-12（後半） | 218点 **115.0%** | 219点 **233.3%** |

**どちらの帯でも、厚いほうが2倍前後に伸びる。総投票額の効果は残る。**

**総投票額を固定してレース番号の効果を見る**:

| 総投票額帯 | 前半 R1-6 | 後半 R7-12 |
|---|---|---|
| <5億円 | 160点 56.8% | 48点 **244.2%** |
| 5-7億円 | 127点 **109.8%** | 109点 85.0% |
| 7-10億円 | 27点 **237.8%** | 124点 89.2% |
| 10億円+ | 0点 — | 156点 282.8% |

**符号が帯ごとに逆転しており、一貫した傾向が無い。**
総投票額を揃えるとレース番号の効果は消える。

### 5.3 結論: 総投票額を使い、レース番号は使わない

| 軸 | 相手を固定しても効果が残るか | 判定 |
|---|---|---|
| **総投票額** | **残る（両帯で約2倍）** | **本物。フィルタに使う** |
| レース番号 | 消える（符号が逆転） | **総投票額の代理変数。使わない** |

的中率（高配当に影響されない指標）でも総投票額の効果が確認できる:

| 条件 | 点数 | 的中率 |
|---|---|---|
| 総投票額 <5億円 | 208 | 4.33% |
| 総投票額 ≥5億円 | 543 | 6.81% |
| 総投票額 ≥7億円 | 307 | **8.47%** |

**レース番号を購入条件に加える必要はない。** 総投票額フィルタが
実質的に後半のレースを選んでいる（5億円以上の通過率は R1で24.7%、R10で88.2%）。

## 6. 当日運用への適用: 絶対額は使えない

> **IMPORTANT**
> §5 のしきい値は**学習データ（JV-Link 履歴 `0B41`）の1m時点**の数字である。
> 当日の速報（`0B31`）が返す `hyosu_total` は 5〜12倍小さく、
> **5億円という絶対額を当日データに当てると1レースも通らない**
> （当日実測: 中央値0.40億円・最大1.75億円）。詳細は README §9。

絶対額が使えない場合の代替として、**その日・その競馬場の中での相対順位**を試した。
スケールが違っても順位は保たれるため、速報値でも使える可能性がある。

| 条件 | 点数 | 回収率(近似) | 95%CI |
|---|---|---|---|
| 全点 | 751 | 140.6% | [94.7, 192.4] |
| 日内上位70% | 596 | 165.1% | [109.0, 228.9] |
| 日内上位50% | 490 | 164.4% | [104.3, 234.0] |
| 日内上位30% | 300 | 173.2% | [88.6, 282.5] |

絶対額（7億円で200.7%）には及ばないが、**上位50〜70%で信頼区間の下側が100%を超える**。

ただし相対順位には実運用上の難点がある。**その日の全レースが終わるまで順位が確定しない**ため、
午前のレースでは「日内順位」を計算できない。使うなら
「前日までの同競馬場の分布から求めた固定しきい値」などに置き換える必要がある。

### 6.0 当日データは「薄い開催だった」のではない

当日データは 2026-09-26 の中京(06)・阪神(09) の22レースのみなので、
「たまたま薄い開催だったのでは」という疑いがある。**履歴を同じ競馬場に
絞って比べた**が、差は消えなかった。

| 比較 | 履歴(同競馬場) | 当日 | 倍率 |
|---|---|---|---|
| 1m 中央値 | 5.84億円（3,190レース） | 0.46億円 | **12.8** |
| 5m 中央値 | 2.68億円 | 0.29億円 | **9.4** |

競馬場を揃えても9〜13倍の差が残る。**開催の質ではなくデータ区分の違い**である。

さらに、倍率は時点によって一定ではない（60m: 8.3倍 / 5m: 8.3倍 / 1m: 11.9倍）。
**単純な定数倍での換算もできない。**

一方で、**分布の形と傾向は一致している**:

| 指標 | 履歴 | 当日 |
|---|---|---|
| q75/q25 比（相対的な散らばり） | 1.69 | 1.65 |
| レース番号との Spearman 相関 | +0.773 | +0.819 |

つまり当日データは**同じものを測っているが目盛りが違う**。
よって「順位」は信頼でき、「絶対額」は信頼できない。

### 6.1 実用的な選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| **A** | 当日取得を履歴と同じ `0B41` に揃える | §5 の知見をそのまま使える。最も筋が良い | スクレイパの変更が必要 |
| **B** | 当日データで分布を測り直し、速報値スケールのしきい値を決める | 変更が小さい | 新しい基準の検証が必要。履歴との対応が不明 |
| **C** | 相対順位（日内上位X%）に置き換える | スケール非依存 | 午前のレースで計算できない |
| **D** | 総投票額フィルタを外す（`min_pool_yen: 0`） | すぐ動く。751点・回収率140.6% | 下側CIが95.6%で100%を割る |

**本筋は A**（§5.2 で総投票額が本物の軸だと確認できたので、この情報を
捨てる案Dは惜しい）。ただし A はスクレイパの変更と再検証を伴うため、
**当面は C（分位点）を採用した**。

### 6.2 採用した設定: 当日スケールに合わせた絶対額 0.4億円

```yaml
strategy:
  min_pool_yen: 40000000     # 当日(0B31)スケールでの下限（0.4億円 ≒ 日内上位50%）
  min_pool_pctile: null      # 分位点モードは使わない（理由は下記）
```

**0.4億円の根拠**: 当日データ（22レース）で「その日の上位50%」に相当する
境界が 0.397億円だった。履歴1m の5億円（上位59.5%）と近い割合を残す水準である。

実装では分位点モード（`AnabaRule.min_pool_pctile`）も用意した。
スケール差に影響されない理想的な方法だが、**実運用の経路では使えない**ことが
分かったため既定では無効にしている（理由は §6.3）。

参考に、履歴データ（1m・2026-02〜07）で分位点モードを検証した結果:

| 条件 | 点数 | 的中率 | 回収率(近似) | 95%CI |
|---|---|---|---|---|
| 絶対額 ≥7億円 | 307 | 8.47% | 200.7% | [112.8, 309.4] |
| 日内上位50% | 437 | 7.78% | 174.1% | [108.9, 253.0] |
| 日内上位40% | 364 | 7.42% | 172.7% | [99.1, 263.7] |
| 日内上位30% | 291 | 8.59% | **202.6%** | [112.9, 311.0] |

**日内上位30%は絶対額7億円（200.7%）とほぼ同等の202.6%**を出している。
分位点でも絶対額と同じ効果が得られること自体は確認できた。

当日データ（2026-09-26・22レース）では、0.4億円でも日内上位50%でも
**10/22レースが通過し、購入2点**が出る（絶対額5億円では0点だった）。

### 6.3 分位点モードを既定にしなかった理由

実装後に検証して分かった**実運用の経路との不整合**である。

`src/pipeline/daily.py` は 2m スナップショットが保存されたレースを
**1〜数レースずつ**判断スレッドへ渡す（全レースまとめてではない）。
この状態で日内分位点を取ると「渡されたレースの中での順位」になってしまう。

実測（当日データ・1レースずつ判断）:

| 判断単位 | 分位点モードの挙動 |
|---|---|
| 22レースまとめて | 10/22レースが通過（正しく機能） |
| **1レースだけ** | **必ず通過**（順位が常に1.0になり、フィルタが無効化される） |

つまりレース単位の運用では、分位点モードは**総投票額の条件を黙って消す**。
これは「条件を満たしたから買った」という誤解を生むため危険である。

対策として `MIN_RACES_FOR_PCTILE`（6レース）を下回る場合は ERROR ログを出す
ようにしたが、根本的にレース単位運用と相性が悪いため既定では無効にした。

分位点モードが使えるのは、**日次バッチで全レースまとめて判定する場合**
（`python -m src.simulator.predict_today` で1日分を一括処理する運用）のみである。

> **NOTE: 絶対額 0.4億円の弱点**
> 1. **根拠が1開催日22レースしかない。** 統計的な裏付けは極めて弱い。
>    開催を重ねたら必ず測り直すこと。
> 2. **速報値のスケールが将来変わると無意味になる。** JV-Link の仕様変更や
>    データ区分の修正で `hyosu_total` の意味が変われば、この値は外れる。
>    §9 の「購入が0点」警告が出たら、まずこの値を疑うこと。
> 3. **履歴データでの検証値をそのまま当てられない。** §5.1 の「7億円で200.7%」
>    のような知見は履歴スケールの話であり、0.4億円が同じ効果を持つ保証はない。
>    **本筋は §6.1 の案A（当日取得を 0B41 に揃える）である。**

## 7. 限界

1. **回収率は確定単勝オッズによる近似**で、端数切捨て前のため過大評価である（冒頭の注意）。
2. **評価期間が短い。** 2026-02〜2026-07 の1,617レース・採用751点のみ。
   §5 の信頼区間は非常に広く、点推定を信じてはならない。
3. **評価期間はモデルの holdout と重なる。** 木の学習（fit）は2026-01-26より前で
   打ち切られているが、early stopping と確率校正にはこの期間を使っている。
   厳密なアウトオブサンプルではない。
4. **しきい値を検証データで選んでいる。** §5.1 の「7億円が最良」は
   この期間を見て選んだ結果であり、上方バイアスを含む。
   レポート本体 §2.2 が自らに課した「しきい値の事前固定」の原則から外れる。
5. **総投票数の傾向（§1〜§4）は11,931レースで安定しており、こちらは信頼できる。**
   不確かなのは §5 の回収率の部分である。

## 8. 再現手順

本レポートの集計は `docs/report/pool_by_race_number_analysis/` のスクリプトで
再現できる。いずれもリポジトリのルートから実行する（既存データのみを読む）。

```bash
D=docs/report/pool_by_race_number_analysis

# §1・§2: レース番号別の総投票数と日内相関
python $D/pool_by_race.py
python $D/pool_isolate.py

# §3・§4: 時間帯・競馬場・曜日・頭数
python $D/pool_detail.py

# §6: 当日データのスケール問題としきい値の換算
python $D/threshold_2m.py    # 当日2m分布と分位点マッチング
python $D/scale_check.py     # 定数倍か否か・分布の形の比較
python $D/venue_fair.py      # 競馬場を揃えた公平な比較

# §5・§6: フィルタ別の採用点数・回収率・信頼区間と、2軸の切り分け
python $D/filter_design.py   # 学習済みモデルが必要
python $D/robust.py          # 同上（ブートストラップ）
python $D/confound.py        # 同上（総票数とレース番号の切り分け）
```

`filter_design.py` / `robust.py` / `confound.py` は
`data/model/simulator/win_anaba.txt` を読むため、先に
`python -m src.simulator.retrain --start-period 202301 --end-period 202607`
を実行しておくこと。
